# 작업 규칙

## 1. 진행 방식

기본값이다. 프로젝트에서 사용자가 바꾸라고 하면 이 절을 고친다.

| 구분 | 규칙 | 강제 (Claude의 hook. 현재 keelkit은 Codex용 hook을 설치하지 않아 Codex는 규칙으로만 지킨다) |
|---|---|---|
| 프로젝트 안 작업 | 파일을 고치기 전에 계획을 말하고 답을 받은 뒤 진행한다 (아래 변경 절차). 승인된 작업의 명령 실행, 브랜치, 커밋, push, PR 작성, `dev` 병합은 묻지 않고 진행한다. 커밋과 PR은 `commit-pr` skill대로 `gh` CLI로 한다. `gh`가 없으면 사용자에게 설치와 `gh auth login`을 안내하고 PR 단계는 보류한다. 설계와 선택 근거는 결과 보고에 적는다 | 권한 허용 (`settings.json`). 계획 · 검수는 규칙으로만 지킨다 |
| 삭제 | 항상 사용자에게 확인을 받는다. 파일 / 폴더, 브랜치, 태그, DB 데이터, 컨테이너 / 볼륨, 변경 되돌리기, 강제 push. 예외: `dev`에 병합이 끝난 `feature/` 브랜치는 로컬과 원격 모두 자동 삭제. `master`, `main`, `dev` 브랜치는 로컬과 원격 모두 삭제하지 않는다 | hook이 실행 전에 확인을 요청 (`guard.py`), `feature/` 삭제는 통과, `master` / `main` / `dev` 삭제는 차단 |
| master / main | merge와 push를 하지 않는다. `dev` → `main` PR은 만들 수 있지만 병합은 사용자가 직접 한다. 브라우저에서 병합 버튼을 누르는 것도 하지 않는다. 예외는 하나다. 원격에 브랜치가 하나도 없으면 빈 커밋으로 `master`를 한 번 만들어 push한다 (`commit-pr` 1번 절). 그 뒤로는 하지 않는다 | 명령은 hook이 차단. 원격이 비어 있을 때의 push만 통과 |
| 환경변수 | 실제 `.env` 하나만 쓴다. 커밋하지 않고 `.gitignore`에 `.env`를 둔다. `.env.example`, `.env.local` 같은 다른 `.env.*` 파일은 만들지 않는다. 값은 출력하거나 문서에 적지 않고, 키 이름과 설명만 `docs/SETUP.md` 3번에 적는다 | hook이 `.env*` 커밋과 `.env.*` 파일 생성을 차단 |
| 묻는 것 | 제품 방향을 바꾸는 결정, 프로젝트 폴더 밖 작업 | - |

### 변경 절차 (파일을 고치는 작업)

1. 계획: 고치기 전에 파일마다 한 줄로 `파일 — 무엇을 — 근거(문서나 코드의 어디)`를 적고 "진행할까요?"로 끝낸다. 작업 하나에 계획 하나이고, 사용자 답을 기다린다. 읽기와 조사는 묻지 않는다.
2. 답: 사용자가 전체를 승인하거나 번호로 일부만 바꾼다 ("2번 빼고"). 한 번 승인하면 그 작업 안에서는 더 묻지 않는다.
3. 다시 묻는 때: 계획에 없던 파일을 고쳐야 할 때, 삭제, 구현 중 방향이 바뀔 때, 제품 방향을 바꾸는 결정.
4. 검수: 실행 뒤 모든 변경의 diff를 읽고 동작, 보안, 규칙(`docs/rules/`), 문서 동기화를 확인한다. 변경이 파일 20개 이상 또는 500줄 이상이면 Claude는 `reviewer` agent로 한다 (Codex는 직접 읽는다). 지적 사항은 고치고 다시 확인한다.
5. 보고: 파일마다 한 줄. `파일 — 변경 이유 — 검수: 통과` 또는 `검수: 지적 N (내용)`.

## 2. 공통

- 코드가 바뀌면 관련 `docs/` 문서도 같은 작업에서 고친다. 같은 내용은 원본 한 곳에만.
- 문제는 증상이 아니라 근본 원인을 본다. 같은 문제가 다른 곳에서도 생기는지 확인한다.
- 규칙, 절차, 금지 사항을 추가하거나 바꾸는 요청은 `harness` skill을 따른다.
- `--no-verify` 같은 hook 우회 옵션을 쓰지 않는다.
- `.gitignore`의 `# keelkit` 아래 줄(`docs/`, `CLAUDE.md`, `.claude/`, `AGENTS.md`, `.agents/` 등)은 지우지 않는다. 다른 `.gitignore`와 합칠 때도 파일을 새로 쓰지 말고 줄만 더한다. 지우는 것은 사용자가 요청할 때만 한다.

## 3. 압축 (compact)

- 단계가 끝나 결정이 문서에 반영되면 다음 단계 전에 사용자에게 `/compact`를 권한다. 구현 도중에는 권하지 않는다.
- 요약에 남길 것: 진행 중인 단계와 남은 작업, 문서에 아직 안 적힌 결정, 고치다 만 파일과 이유, 실패한 테스트 원문.
